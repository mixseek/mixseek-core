# パターン比較分析: B (Fable 5 単独) vs C (Fable 5 + Workflow)

> 対象: `refactor-plans/outputs/b-fable5/` と `refactor-plans/outputs/c-fable5-wf/`
> 同一の共通ブリーフ（`prompts/_shared-brief.md`）に対する成果物を、**同一トピックを同じ行に揃えて**比較した。
> B と C は**同じモデル（Fable 5）**で、差は「単発実行」か「ワークフロー（11サブシステムを並列分析する
> サブエージェント群 → 統合エージェント）」かのみ。つまり本比較は **同一モデルにおける単発 vs 並列ワークフロー
> の差** を測るものになっている。
> パターンA（Opus 4.8）はここでは対象外（→ `../a-vs-b/`）。

## 1. 全体サマリ

| 観点 | B (Fable 5 単発) | C (Fable 5 + Workflow) |
| --- | --- | --- |
| 候補数 | 19件（C/M/S/E/U/X 系） | **49件**（11サブシステム × 各4〜6候補 → 統合） |
| 構成 | サブシステム別6ファイル | サブシステム別11ファイル＋横断1＋統合注記(※1〜6) |
| 分析の深さ | 主要ファイルを広く一巡。設計の臭いを的確に把握 | 各サブシステムを精読し**行番号・実バグ**まで到達 |
| 強み | 候補が厳選され読みやすい・優先順位が明快・再発防止策(ruff)の提案 | 網羅性・**実バグの発見**・レイヤ違反/循環依存などアーキ負債の特定 |
| 弱み | 細部の見落とし（TomlSource重複・usage_infoバグ等）・分析範囲が中核ファイル寄り | 候補過多で取捨に労力・候補間の重複を統合で吸収（生のファンアウトは重複を産む） |

**結論: 網羅性と発見の深さでは C (Workflow) が明確に上回る。** 同一モデルでも、サブシステムを分担して
精読させたことで、単発の B が触れなかった**実害あるバグ**（トークン集計が常に0になる usage_info キー不整合）や
**アーキテクチャ負債**（utils⇔config 循環依存、storage→agents のレイヤ逆転）まで掘り当てた。
一方で **計画としての「使いやすさ」は B が上**：19件は優先順位を付けて即着手しやすく、49件は価値の高いものと
小粒な掃除が混在し、取捨選択の一手間が要る。

> 端的に言えば、**C は「監査レポート」、B は「実行計画」** に近い。最良の運用は
> 「C の網羅的な発見を母集団とし、B のような厳選・優先順位付けで実行計画に落とす」こと。

## 2. コード検証で確定した事実（C が単独で発見し、B が見落とした項目）

C の目玉である「単発では出てこなかった発見」を実コードで確認した。**4件すべて事実**だった。

| 検証項目 | 結果 | 意味 |
| --- | --- | --- |
| **usage_info キー不整合（C最優先・順1）** | member 側は `prompt_tokens`/`completion_tokens` で格納（`plain.py:118` 他）、`leader/tools.py:91` は `input_tokens`/`output_tokens` で参照 | **トークン集計が常に0になる実バグ**。さらに pydantic-ai の `RunUsage` の正式属性とも食い違い両側が壊れている。A・B とも未発見、C のみが最優先候補として特定 |
| **TestModel 暗黙置換（C 04-候補5）** | `auth.py:106` で `os.getenv("PYTEST_CURRENT_TEST")` → `auth.py:367` で `TestModel()` を無条件返却 | モジュール自身の "NO implicit fallbacks"(`auth.py:351`) と矛盾する隠れた制御フロー。C のみ指摘 |
| **metrics/base.py LSP違反（C 02-候補3）** | `base.py:198` に `async def evaluate(  # type: ignore[override]` | シグネチャ非互換オーバーライド。これが `evaluator.py` の isinstance 分岐を強いる。C のみ指摘 |
| **leader_board DDL 二重定義（C 05-候補1）** | `schema.py:47` と `aggregation_store.py:177` で同一テーブルを二重 CREATE、シーケンスも両方で作成 | `IF NOT EXISTS` の先勝ちでスキーマドリフトの温床。C のみ独立候補化 |

加えて C は、B が「触らない」と判断した **TomlSource の重複**（`config/sources/` の6〜8ファイルが定型を再実装）を
正しく候補化している。これは `a-vs-b` の検証で「実在する重複」と確認済みであり、**C は B の盲点を補正**している
（同じ盲点を A も補正していた）。

## 3. トピック別の所感（要点）

詳細は [comparison.csv](comparison.csv)（全51行）を参照。差が大きかった点を抜粋する。

### C が単独で発見した高価値項目（B に対応候補なし）

- **実バグ／バグ寸前**: usage_info キー不整合（順1・実害あり）、TestModel 暗黙置換、
  CLI の `typer.Exit` 誤捕捉による終了コード破壊（06-候補4）、UIサービスの接続リーク（07-候補3）、
  リトライ判定の例外型名 文字列比較（03-候補5）。
- **アーキテクチャ負債**: utils⇔config 循環依存の根因特定（01-候補6, 10-候補2）、
  storage→agents のレイヤ逆転＋pandas の公開契約露出（05-候補5）、models→CLI 依存（result.py, 08-候補5）。
- **大型 DRY**: Member Agent 4実装の execute() コピー（各120行、09-候補1）、
  構造化LLM呼び出しの二重実装（11-候補4）、storage のリトライループ4重複。
- **規約順守の踏み込み**: storage の共通ロガー完全不在（grep 0件）、構造化ログの不徹底を
  定量化（`extra=` は 105 箇所中 7 箇所のみ）。

### B が優れる／B 独自の価値

- **優先順位と可読性**: 19件に明快な着手順とフェーズ分け。49件の C より実行計画として直接使える。
- **再発防止の仕組み化**: `os.getenv` を ruff banned-api で禁止（X2）、Pydantic deprecation を
  `filterwarnings=error` で検知（X4）。C も一部で ruff 活用に触れるが、B は明示的。
- **CLI→UI の env 伝搬を型契約化（U3）**: `UIBridgeSettings.to_env()/from_env()` という具体設計。
  C は env 伝搬を「棚卸しして引数渡しへ」と扱い、この特定問題への解像度は B がやや高い。

### 互角・観点差

- schema分割／manager共通化／views分離／evaluation_config統合／_execute_impl分割／例外階層統一
  などの**中核候補は両者ともほぼ同じ結論**に到達。C は行番号と付随改善が多く、B は提示が簡潔。
- integration_hooks は両者とも「本番利用1箇所」を正しく特定（検証済）。B は「削除」を主軸に純減を強調、
  C は「未使用部を削り残部を分割」とより保守的＋aiohttp 依存除去という副次効果も発見。製品判断次第。

## 4. ワークフロー（並列ファンアウト）の効果と副作用

本比較は「同一モデルで単発 vs ワークフロー」を見るものなので、ワークフロー自体の損得を記録する。

**効果（プラス）**
- **網羅性**: 11サブシステムを漏れなく精読 → 中核ファイル偏重だった B が触れなかった
  workflow/utils/observability/prompt_builder/framework 層の負債まで拾えた。
- **深さ**: 各エージェントが担当を深掘りするため、行番号・grep 結果・実バグに到達。単発の注意資源では
  ここまで沈まない。

**副作用（マイナス）**
- **候補の重複**: 同一の横断課題（例外階層・workspace・Logfire初期化・LLM Mixin）に複数サブエージェントが
  独立到達し、統合エージェントが ※1〜6 でマージする必要があった。生のファンアウトは重複を産む。
- **粒度のばらつき**: 49件に「実害あるバグ」と「sleep(5)のマジックナンバー」「未使用関数削除」が混在。
  優先順位表で緩和されているが、取捨選択のコストは B より高い。
- **コスト**: サブエージェント11＋統合のワークフローは単発より大幅に高コスト（トークン・時間）。

## 5. 総合評価と推奨

**発見力・網羅性の勝者: C (Workflow)。** 同一モデルでも並列精読により、単発の B が見落とした
**実バグとアーキテクチャ負債**を多数掘り当てた。特に usage_info の実バグは、リーダーボードの
トークン/コスト集計に直結する実害であり、発見できた価値は大きい。

**計画としての完成度: B が上。** 厳選された19件＋明快な優先順位は、そのまま着手できる実行計画になっている。

推奨する運用:

1. **発見フェーズは C 方式**（サブシステム並列精読）で母集団を最大化する。特に「バグ」「レイヤ違反」
   「循環依存」のような深掘りでしか出ない項目は、単発では取りこぼす。
2. **C の49件を B のように再優先順位付け**して実行計画化する。実バグ（順1の usage_info 等）を
   最優先、横断基盤（例外/ロガー/workspace/auth）を次に、大型分割を基盤確立後に——という
   C 自身のフェーズ分けは妥当なので、それを母体に B 的な厳選を重ねる。
3. **再発防止策は B から採用**：ruff banned-api（os.getenv 禁止）、`filterwarnings=error`、
   ruff B904/G系の機械化を計画に組み込む。
4. C が「触らない」とした項目はほぼなく、逆に B が「触らない」とした TomlSource を C が補正している。
   **B 単独運用なら TomlSource の見落としに注意**。

> 注: 本分析は計画ドキュメントの比較であり、リファクタリングの実装は行っていない。
> コード検証は主張の真偽確認のための読み取り専用調査のみ（usage_info / TestModel / LSP / DDL の
> 4件はいずれも実コードで確認済み）。
