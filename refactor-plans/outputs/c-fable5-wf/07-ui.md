# リファクタリング計画: ui サブシステム

## 概要（責務と依存の現状）

`src/mixseek/ui/` は Streamlit 製の Web UI。実測（wc -l、.py のみ）で約 2,900 行・26 ファイル。

- **エントリポイント**: `app.py`（124行）。ページ登録・ロギング/Logfire 初期化・ワークスペース検証を担う。
- **pages/**: `1_execution.py`（212行）/ `2_results.py`（100行）/ `3_history.py`（145行）。
  セッション状態管理とポーリングループを含む。
- **services/**: `execution_service.py`（**772行**）/ `round_service.py`（256行）/
  `leaderboard_service.py`（177行）/ `history_service.py`（137行）/ `config_service.py`（94行）。
  DuckDB 読み取り・進捗 JSON ファイル読み取り・オーケストレーション実行を担う。
- **components/**: 表示部品 10 ファイル（各 34〜125 行、問題なし）。
- **models/**: pydantic モデル 5 ファイル（execution/round_models/config/leaderboard/history）。
- **utils/**: `db_utils.py`（78行）/ `duckdb_conn.py`（36行）/ `workspace.py`（40行）。

依存方向: pages → components → services → utils/models。コア側へは
`mixseek.orchestrator`（`Orchestrator`, `load_orchestrator_settings`）、`mixseek.core.auth`、
`mixseek.observability`、`mixseek.config.logging/logfire`、`mixseek.utils.env` に依存。
データ連携はコード共有ではなく **DuckDB（mixseek.db）と進捗 JSON ファイルを介した疎結合**で、
この方針自体は妥当。問題は UI 内部のユーティリティ重複と `execution_service.py` への責務集中。

## 評価サマリ（観点1〜5）

### 観点1: 責務と依存

`execution_service.py` に 5 つの責務が同居している。
(a) 進捗 JSON 読み取り（`_read_progress_from_file` 38-135行、`get_all_teams_execution_status` 178-237行）、
(b) 同期実行（`run_orchestration` 240-379行、Logfire 初期化込み）、
(c) バックグラウンド実行とグローバル状態管理（`run_orchestration_in_background` 382-479行、
モジュールレベル辞書 `_execution_states` / `_execution_results` / `_execution_errors` 27-35行）、
(d) DuckDB 読み取り（`get_execution_result` 513-622行、`get_team_ids_for_execution` 625-704行）、
(e) ログファイル読み取り（`get_recent_logs` 707-772行）。他サービスは単一責務で健全。

### 観点2: 設計上の臭い

- **DB 接続ヘルパーの三重化**: `utils/db_utils.py:get_db_connection`（DB不在→None）と
  `utils/duckdb_conn.py:get_read_connection`（DB不在→FileNotFoundError送出）が同目的で仕様不一致。
  さらに `execution_service.py:573,681` は両者を使わず `duckdb.connect` を直接呼ぶ。
  利用側も分裂: round_service→db_utils、leaderboard/history→duckdb_conn。
- **get_workspace_path の二重定義**: `db_utils.py:21-44`（`os.getenv` 直読み・ValueError）と
  `workspace.py:8-17`（共通 `mixseek.utils.env` 経由・WorkspacePathNotSpecifiedError）が同名で並存。
- **「実行中ガード」のコピペ**: `execution_service.py` の 526-561 行と 639-670 行は
  状態辞書チェック＋進捗ファイル走査がほぼ同一コード（約 35 行 ×2）。
- **Logfire 初期化の重複**: `app.py:60-80`、`execution_service.py:270-289`、
  `cli/utils.py:300` 付近・`cli/commands/ui.py:87` に同パターンの env 読み取り＋ `setup_logfire` が散在。
- **グローバル可変辞書**: `execution_service.py:27-35` の 3 辞書はロックなしで
  バックグラウンドスレッドから書き込まれ、エントリ削除もないため長時間稼働でリークする。
- **古いパターン**: pydantic v2 で非推奨の `class Config`（`models/execution.py:55,91`、
  `models/config.py:40,155`、`models/history.py:37`）。`db_utils.py:11-12` と `round_service.py:13` の
  docstring は存在しない `build/lib/mixseek_ui/` を参照（ビルド成果物由来の死に参照）。
- **マジックナンバー**: `pages/1_execution.py:74-76` の「DuckDB ロック解放待ち `time.sleep(5)`」。

### 観点3: AGENTS.md 自己ルール違反

- **300 行超**: `execution_service.py` 772 行（唯一の違反。round_service は 256 行で許容内）。
- **`os.getenv` 直接呼び出し**: `app.py:37-44,60,66-67`（7箇所）、`db_utils.py:38`、
  `execution_service.py:272,279-280`。規約の共通 config モジュール経由になっていない。
- **ロガー**: `execution_service.py:23` 等は `logging.getLogger(__name__)` を使用
  （`setup_logging` 経由で構造化出力されるため実害は小。ただし round_service / leaderboard_service /
  history_service は例外をログすら出さず握りつぶす — 観点4参照）。

### 観点4: エラー処理・型

- **方針の不一致**: db_utils は None 返却、duckdb_conn は FileNotFoundError 送出、
  round_service は全関数で `except Exception:` → None/空返却（ログなし。59-62, 100-104, 143-147,
  187-191, 252-256行）、execution_service は debug/warning ログ付きで握りつぶし。3 流派が混在。
- **接続リーク**: `leaderboard_service.py:43,100,157` と `history_service.py:64,120` の
  `conn.close()` は try 本文内にあり、クエリ例外時にクローズされない（round_service は finally で正しい）。
- **型注釈**: 全関数に戻り値型あり。mypy 通過水準で概ね良好。
  `cast(LogFormatType, os.getenv(...))` の多用（app.py / execution_service.py）は設定モジュール化で解消可能。

### 観点5: テスト被覆

`tests/ui/` に単体＋integration あり（計約 1,400 行）。
- 厚い: `test_execution_service.py`（269行・10テスト。ただし対象は `run_orchestration` の入口、
  `get_recent_logs`、`_get_failed_teams_from_progress_files` のみで、バックグラウンド実行・
  DuckDB 読み取り系は未カバー）、`test_config_service.py`（170行）、`test_history_service.py`（149行）、
  `test_leaderboard_service.py`（146行）、`test_performance.py`（148行）。
- 薄い/なし: **`round_service.py` と `db_utils.py` に対応するテストが存在しない**（grep で参照ゼロ）。
  components/ の直接テストなし（pages の integration smoke が 36〜63 行のみ）。
  `test_duckdb_conn.py`（36行）/ `test_workspace_utils.py`（38行）は最低限あり。

## リファクタリング候補

### 候補1: execution_service.py（772行）の責務分割

- **対象**: `src/mixseek/ui/services/execution_service.py`
- **問題**: 観点1（5責務の同居）、観点2（実行中ガードのコピペ、グローバル可変辞書、duckdb 直接続）、
  観点3（300行ルール違反・サブシステム内最大、`os.getenv` 直接使用 272,279-280行）。
- **影響度**: 高（実行ページの中核。バグ時はタスク実行 UI 全体が機能不全）
- **リスク**: 中（スレッド＋ポーリングのタイミング依存ロジックを含む）
- **推奨アプローチ**: 公開 API（pages からの import 6 関数）を維持したまま 4 ファイルへ分割。
  1. `progress_reader.py`: 進捗 JSON 読み取り（`_read_progress_from_file` 等 3 関数）。
     「実行中か判定」ロジックを 1 関数に共通化し、526-561 / 639-670 行の重複を解消。
  2. `execution_state_store.py`: グローバル 3 辞書を `threading.Lock` 付きストアクラスへ置換し、
     完了エントリの上限/掃除を導入。
  3. `orchestration_runner.py`: `run_orchestration` / `run_orchestration_in_background`。
     Logfire 初期化は候補4の共通関数を呼ぶだけにする。
  4. `execution_repository.py`: DuckDB 読み取り 2 関数（候補2の共通接続ヘルパーを利用）。
     `get_recent_logs` は `log_reader.py` または utils へ移動。
- **関連テスト**: `tests/ui/test_execution_service.py`（269行）が入口を保護。ただし
  バックグラウンド系・DuckDB 系は未カバーのため、**分割前に特性テストを追加**してから着手する。
- **工数感**: L

### 候補2: DB 接続・ワークスペース取得ユーティリティの一本化（db_utils 廃止）

- **対象**: `src/mixseek/ui/utils/db_utils.py`、`utils/duckdb_conn.py`、`utils/workspace.py`、
  利用側 `services/round_service.py:19`
- **問題**: 観点2（同名 `get_workspace_path` の二重定義、接続ヘルパー三重化、死に docstring 参照）、
  観点3（`db_utils.py:38` の `os.getenv` 直接使用）、観点4（None 返却 vs 例外送出の仕様不一致）。
- **影響度**: 高（UI の全 DB アクセスの土台。エラー仕様が統一され候補3の前提になる）
- **リスク**: 低（薄いユーティリティ層。挙動差は「DB 不在時」の扱いのみで呼び出し箇所は少数）
- **推奨アプローチ**: `duckdb_conn.py` に一本化し `db_utils.py` を削除。
  ワークスペース取得は `workspace.py`（共通 `mixseek.utils.env` 経由）のみ残す。
  接続は `contextlib.contextmanager` 化（`with open_read_connection() as conn:`）して
  close 漏れを構造的に防ぐ。DB 不在/ロック時の戻り値仕様（None 返却）をドキュメント込みで統一。
- **関連テスト**: `test_duckdb_conn.py`（36行）/ `test_workspace_utils.py`（38行）あり。
  db_utils のテストはないため、移行時に round_service 側のテスト（候補3）で担保する。
- **工数感**: S

### 候補3: サービス層のエラー処理・接続クローズの一貫化 ＋ round_service テスト追加

- **対象**: `services/round_service.py`、`services/leaderboard_service.py`、`services/history_service.py`
- **問題**: 観点4（round_service の全関数がログなし `except Exception` 握りつぶし、
  leaderboard/history の `conn.close()` が finally 外で例外時に接続リーク）、
  観点5（**round_service にテストが存在しない**）。
- **影響度**: 中（障害時に原因がログに残らず調査不能になる。リークは長時間セッションで顕在化）
- **リスク**: 低（読み取り専用クエリのみ。外部仕様は「失敗時に空/None」を維持）
- **推奨アプローチ**: 候補2のコンテキストマネージャへ全サービスを移行し close 漏れを解消。
  例外は共通ロガーで `logger.warning(..., exc_info=True)` を出してから空/None を返す方針に統一。
  行データ→モデル変換（`from_db_row` / タプル添字アクセス）の整理も同時に実施。
  着手前に round_service の単体テスト（5 関数 × 正常/DB不在/クエリ失敗）を追加する。
- **関連テスト**: `test_leaderboard_service.py`（146行）/ `test_history_service.py`（149行）が安全網。
  round_service 分は新規作成が前提条件。
- **工数感**: M

### 候補4: ロギング/Logfire 初期化の共通化と os.getenv 排除

- **対象**: `app.py`（36-80行）、`services/execution_service.py`（270-289行）、
  （参考: `cli/utils.py` / `cli/commands/ui.py` の同パターン）
- **問題**: 観点2（同一の env 読み取り＋初期化コードが UI 内 2 箇所＋CLI 側に重複）、
  観点3（`os.getenv` 直接呼び出し計 10 箇所超。共通 config モジュール経由の規約違反）。
- **影響度**: 中（ログ設定の変更が複数箇所の同期修正を要求し、現に `cast` だらけで型安全でない）
- **リスク**: 低（初期化処理のみで業務ロジックに非依存。既存テストが厚い）
- **推奨アプローチ**: `mixseek.config.logging` 側に `LoggingConfig.from_env()` 相当の
  ファクトリを追加（`LogfireConfig.from_env()` は既存）。UI/CLI はそれを呼ぶだけにし、
  `cast(LogFormatType, os.getenv(...))` パターンを全廃。app.py の初期化ブロックは
  `ui/bootstrap.py` 等へ関数として切り出し、app.py はページ定義に専念させる。
- **関連テスト**: `tests/cli/commands/test_ui_logfire.py`（224行）、
  `tests/ui/integration/test_logfire_integration.py`（152行）、`test_app_entrypoint.py`（42行）と厚い。
- **工数感**: M

### 候補5: 実行ページのポーリング制御整理（sleep(5) マジックナンバー解消）

- **対象**: `src/mixseek/ui/pages/1_execution.py`（74-83, 186-198行）
- **問題**: 観点2（ロック解放待ち `time.sleep(5)` のハードコード、task_prompt の
  3 段フォールバック取得ロジックがページに埋め込み）、観点5（integration smoke 36 行のみ）。
- **影響度**: 低〜中（UX 上の 5 秒固定ブロックと、ページの可読性・テスト容易性）
- **リスク**: 低（表示制御のみ。サービス層 API は不変）
- **推奨アプローチ**: ポーリング間隔・完了後待機秒数を `ui/constants.py` へ定数化。
  完了後の固定 sleep は「DB 接続成功までの指数バックオフ付きリトライ」（候補2のヘルパーで判定）に
  置換。task_prompt 解決ロジックは execution_service（候補1の repository）へ関数として移動。
- **関連テスト**: `tests/ui/integration/test_execution_page.py`（36行）。表示分岐のテスト追加が望ましい。
- **工数感**: S

### 候補6: pydantic v2 非推奨 `class Config` の ConfigDict 移行

- **対象**: `models/execution.py:55,91`、`models/config.py:40,155`、`models/history.py:37`
- **問題**: 観点2（古いパターン。pydantic>=2.12.5 環境で v1 互換の `class Config` は非推奨、
  将来バージョンで削除予定）。
- **影響度**: 低（現状動作に問題なし。将来の pydantic アップグレードへの備え）
- **リスク**: 低（機械的置換。`model_config = ConfigDict(use_enum_values=True)` へ書き換えのみ）
- **推奨アプローチ**: 5 箇所を `ConfigDict` へ一括置換し、deprecation warning をテストで検知する
  設定（`filterwarnings = error::DeprecationWarning` 等）の導入を検討。
- **関連テスト**: 各モデルはサービステスト経由で間接カバー。シリアライズ挙動の回帰は
  `test_history_service.py` / `test_execution_service.py` で検出可能。
- **工数感**: S

### 推奨着手順

依存関係から **候補2 → 候補3 → 候補4 → 候補1 → 候補5 → 候補6** を推奨。
候補2が接続ヘルパーの土台を作り、候補3・候補1がその上に乗る。候補1は事前の特性テスト追加が前提。
候補6は独立しており、いつでも実施可能。
