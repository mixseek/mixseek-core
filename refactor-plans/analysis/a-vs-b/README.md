# パターン比較分析: A (Opus 4.8 単独) vs B (Fable 5 単独)

> 対象: `refactor-plans/outputs/a-opus48/` と `refactor-plans/outputs/b-fable5/`
> 同一の共通ブリーフ（`prompts/_shared-brief.md`）に対する2モデルのリファクタリング計画を、
> **同一トピックを同じ行に揃えて**比較し、内容の違いと優劣の所感をまとめた。
> パターンC（Fable 5 + Workflow）はここでは対象外。

## ファイル構成

| ファイル | 内容 |
| --- | --- |
| [comparison.csv](comparison.csv) | トピック単位で A/B の項目を同一行に揃えた比較表（影響度・リスク・工数・所感・優位） |
| 本 README | 比較の要約、コード検証で確定した事実、総合評価 |

## 1. 全体サマリ

| 観点 | A (Opus 4.8) | B (Fable 5) |
| --- | --- | --- |
| 候補数 | 15件（R1〜R15） | 19件（C/M/S/E/U/X 系） |
| 構成 | サブシステム別6ファイル＋優先度表 | サブシステム別6ファイル＋二重化マップ等 |
| 強み | 横断課題（ロガー統一）の正面対応・CLI棚卸しの網羅性・着手順の設計 | 根本原因の特定・コード検証の精度・段階PR設計・独自候補の多さ |
| 弱み | 抽象的な記述が残る・デッドコードを分割提案・独自洞察が少なめ | TomlSource重複の見落とし・ロガー統一の候補化漏れ |

**結論: 総合的には B (Fable 5) が優れている。** 特に「根本原因の特定」「主張の検証可能性（行番号・数値・コード例）」
「段階的PR設計」で差をつけた。ただし A も **B が見落とした重要候補を2件**（TomlSource共通基底・共通ロガー統一）
押さえており、A 独自の価値も明確に存在する。**最良の計画は両者のマージ**で得られる（後述）。

## 2. コード検証で確定した事実（優劣判断の根拠）

所感を主観で終わらせないため、両者の主張が食い違う／検証可能な箇所を実コードで確認した。

| 検証項目 | 結果 | 判定 |
| --- | --- | --- |
| 300行超ファイル数 | **実測19個**（ブリーフは「20」） | A・B とも「19」で正確。ブリーフ側が誤差 |
| `integration_hooks` の本番呼び出し | `agents/member/factory.py` の **1箇所のみ** | **B の「デッドコード→削除」(X1) が正しい**。A の「分割+singleton解消」(R9) は死んだコードの再構築で的外れ |
| 200行超の関数 | `orchestrator._execute_impl` の **202行が唯一1件** | **B の「唯一の200行違反」(E1) が精密に正しい**。A は「約200行」と曖昧で140行級も違反扱い |
| `config/sources/` の TomlSource | 8クラスが各々 `PydanticBaseSettingsSource` を継承し `get_field_value`/`prepare_field_value`/`__call__`/`_load*` を再実装。`field_mapper` 利用は **3クラスのみ** | **A の「共通基底抽出」(R4) は実在する重複**。B は「触らなくてよい」と**誤判定**（ファイルは小さいがクロスファイル重複を見落とし） |

検証コマンドの要旨: `wc -l` による行数実測、`grep` による `integration_hooks` 参照追跡、
`ast` モジュールによる関数長解析、`sources/` の継承構造と `field_mapper` 参照の確認。

## 3. トピック別の所感（要点）

詳細は [comparison.csv](comparison.csv) を参照。ここでは差が大きかった行を抜粋する。

### B が明確に勝った項目

- **integration_hooks（A:R9 / B:X1）** — 最大の判断差。検証どおり本番呼び出しは1箇所のみで、
  B の「削除」診断が正しい。A は死んだコードの分割という労力配分ミス。
- **新旧設定モデル統合（A:R6 / B:M1）** — 最重要課題という認識は共通だが、B は
  「移行完了とコメントされながら旧モデル残存」「`timeout_seconds` 制約が新旧で乖離（`ge=10,le=600` vs `ge=0`）」
  といった具体的証拠を挙げ、3系統を別PRに分けて段階実施する設計まで提示。A は方向性のみで抽象的。
- **orchestrator の長大メソッド（A:R11 / B:E1）** — B は AST 解析で「202行・唯一の違反」と断定し
  抽出後のコード例まで提示。A は「約200行」と曖昧。
- **B 独自の候補群** — M2（LLMパラメータ Mixin / 制約乖離の根本原因への構造的解法）、
  M3（`get_*_for_metric` 統合）、U2（観測性初期化の3重複の一本化）、U3（CLI→UI の env 伝搬を型契約化）、
  E3（カスタムメトリクスローダー分離）、X3（例外階層統一）、X4（Pydantic v1 残滓）は
  いずれも A に対応候補がない、または部分言及にとどまる。B の探索の深さと網羅性が表れている。

### A が勝った／A 独自の価値がある項目

- **TomlSource 共通基底（A:R4）** — 検証どおり実在する DRY 違反を A だけが候補化。B は誤って却下。
- **共通ロガー統一（A:R15）** — `logging.getLogger` 直生成19+箇所・命名バラバラという
  AGENTS.md 規約（共通ロガー使用）違反への正面対応。B は初期化の一本化（U2）に寄り、
  各モジュールのロガー取得作法の統一を候補化していない。A は「最初に着手すべき低リスクな足場」と
  位置づけており、着手順の設計思想も明快。
- **CLI 層の棚卸し（A:R13）** — 300行超 CLI 5ファイルを網羅列挙。B は config.py 1ファイルに絞る。

### 引き分け / 観点差

- **member_agent.py（A:R12 / B:M1内）** — A は規約準拠の物理分割として独立候補化、
  B は構造統一（旧Config縮小）の副産物として扱う。狙いが異なり優劣は一概に言えない。

## 4. スタイルの違い

| | A (Opus 4.8) | B (Fable 5) |
| --- | --- | --- |
| 記述の粒度 | サブシステムの責務を俯瞰し、着手順（依存順）を重視 | 行番号・削減見込み行数・コード例で具体化 |
| 検証の度合い | 構造の読み取り中心、定量検証はやや弱い | `wc -l`/AST/grep で機械的に棚卸し（調査メモを明記） |
| 安全網の意識 | テスト被覆の厚薄を各候補に付記 | 同左＋「手薄領域は先にテスト追加」を具体的手順で指示 |
| 独自洞察 | ロガー統一・TomlSource重複・CLI網羅 | 制約乖離の根本原因・デッドコード・初期化重複・型契約化 |
| 弱点 | 抽象表現とデッドコード分割提案 | TomlSource重複の見落とし・ロガー統一の漏れ |

## 5. 総合評価と推奨

**勝者: B (Fable 5)。** 根本原因の特定力、主張の検証可能性、段階的な実行設計、候補の網羅性で上回る。
特に integration_hooks のデッドコード診断と設定モデル乖離の具体的証拠は、実装着手の意思決定に
直結する価値が高い。

ただし **A を捨てるべきではない。** 実運用の最良計画は次のマージで得られる:

1. **ベースは B** を採用（候補の精度・段階設計が優れるため）。
2. **B に A の独自候補を追加**:
   - A:R4（TomlSource 共通基底抽出）— 検証済みの実在重複。B の「触らない」判断を覆して採用。
   - A:R15（共通ロガー get_logger 統一）— B:U2（初期化一本化）と相補的。U2 を実施しつつ
     各モジュールのロガー取得作法も R15 で統一する。
   - A:R13 の CLI 5ファイル網羅 — B:U4（config.py のみ）の対象を A の一覧まで広げる。
3. **着手順は A の設計思想**（低リスクな足場固め → 安全網が効く分割 → 高リスクな統合）を踏襲しつつ、
   B のクイックウィン（M3/C2/E1/X1/U4/X4）を最初のスプリントに置く。

> 注: 本分析は計画ドキュメントの比較であり、リファクタリングの実装は行っていない。
> コード検証は主張の真偽確認のための読み取り専用調査のみ。
